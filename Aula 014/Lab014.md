## Cenário: O Site do Curso Está no Ar... E Agora?

### O Desafio

Na aula anterior, deployamos a página do curso de ADS no EKS. O site está acessível via LoadBalancer, os pods estão rodando... **Missão cumprida?**

Não. Imagine o seguinte:
- São 2h da manhã. O site cai. Ninguém percebe até o dia seguinte.
- O período de inscrições começa. O tráfego triplica. A aplicação fica lenta.
- Um deploy novo introduz um bug. Requisições retornam erro 500. Quando começou?
- Um pod está consumindo memória excessiva. A conta da AWS dispara.

### O Problema: "Funcionou no Deploy" Não É Suficiente

Sem monitoramento, você está **voando às cegas**:
- Não sabe se a aplicação está saudável
- Não sabe quando problemas começaram
- Não é alertado antes que os usuários percebam
- Não tem dados para otimizar performance

### A Solução: Os 3 Pilares da Observabilidade

| Pilar | O que é | Ferramenta AWS |
|-||-|
| **Logs** | Registros detalhados de eventos | CloudWatch Logs |
| **Métricas** | Números que medem comportamento | CloudWatch Metrics + Container Insights |
| **Alertas** | Notificações automáticas de anomalias | CloudWatch Alarms |

> 💡 **Analogia:** Monitoramento é como o painel de um carro. Sem ele, você dirige sem saber a velocidade, o nível de combustível ou a temperatura do motor. Pode funcionar por um tempo... até não funcionar mais.

## Seção 2: Configurando CloudWatch Logs para o EKS

> **Contexto:** Por padrão, os logs dos pods no EKS não vão para lugar nenhum persistente — quando o pod morre, os logs vão junto. Precisamos configurar um mecanismo para enviar logs dos containers para o CloudWatch Logs, onde ficam armazenados, pesquisáveis e podem disparar alertas.
>
> **Conceitos-chave:**
> - **Fluent Bit:** Agente leve de coleta de logs (usado pela AWS como padrão no EKS). Roda como DaemonSet — um pod em cada node
> - **DaemonSet:** Tipo de recurso K8s que garante que um pod rode em TODOS os nodes do cluster
> - **Log Group:** Agrupamento lógico de logs no CloudWatch (como uma "pasta")
> - **Log Stream:** Sequência de eventos dentro de um Log Group (cada pod gera um stream)
> - **Namespace do CloudWatch:** Separação lógica de métricas (ex: `ContainerInsights` vs `AWS/EKS`)

### 2.1 Criando o Log Group

```bash
# Criar log group para os containers do EKS
aws logs create-log-group \
  --log-group-name $LOG_GROUP \
  --region $AWS_REGION

# Definir retenção de 7 dias (economia para lab)
aws logs put-retention-policy \
  --log-group-name $LOG_GROUP \
  --retention-in-days 7

echo "Log Group criado: $LOG_GROUP"
```

### 2.2 Criando Namespace e Service Account para Fluent Bit

```bash
# Criar namespace para observabilidade
kubectl create namespace amazon-cloudwatch

# Criar ConfigMap com nome do cluster (Fluent Bit precisa dessa info)
kubectl create configmap fluent-bit-cluster-info \
  --namespace amazon-cloudwatch \
  --from-literal=cluster.name=$CLUSTER_NAME \
  --from-literal=http.server=On \
  --from-literal=http.port=2020 \
  --from-literal=logs.region=$AWS_REGION
```

### 2.3 Configurando Permissões IAM para Fluent Bit

```bash
# Criar política IAM para CloudWatch Logs
cat > cloudwatch-policy.json << 'EOF'
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "logs:CreateLogGroup",
        "logs:CreateLogStream",
        "logs:PutLogEvents",
        "logs:DescribeLogGroups",
        "logs:DescribeLogStreams"
      ],
      "Resource": "*"
    }
  ]
}
EOF

# Anexar política à role dos nodes (já criada no Lab013)
aws iam put-role-policy \
  --role-name EKSNodeRole-ADS \
  --policy-name CloudWatchLogsAccess \
  --policy-document file://cloudwatch-policy.json

echo "✅ Permissões CloudWatch configuradas"
```

### 2.4 Deployando Fluent Bit como DaemonSet

```bash
# Aplicar manifesto oficial da AWS para Fluent Bit
kubectl apply -f https://raw.githubusercontent.com/aws-samples/amazon-cloudwatch-container-insights/latest/k8s-deployment-manifest-templates/deployment-mode/daemonSet/container-insights-monitoring/fluent-bit/fluent-bit.yaml

# Verificar se Fluent Bit está rodando em todos os nodes
kubectl get pods -n amazon-cloudwatch

# Ver logs do Fluent Bit (verificar se está coletando)
kubectl logs -n amazon-cloudwatch -l k8s-app=fluent-bit --tail=10
```

> [!NOTE]
> **Resultado Esperado:** Um pod Fluent Bit rodando em cada node (2 pods se tiver 2 nodes).

### 2.5 Verificando Logs no CloudWatch

```bash
# Aguardar 1-2 minutos para logs chegarem, depois verificar
aws logs describe-log-streams \
  --log-group-name $LOG_GROUP \
  --order-by LastEventTime \
  --descending \
  --limit 5 \
  --query 'logStreams[].logStreamName'

# Buscar logs recentes
aws logs filter-log-events \
  --log-group-name $LOG_GROUP \
  --start-time $(date -d '5 minutes ago' +%s)000 \
  --limit 10 \
  --query 'events[].message' \
  --output text
```



## Seção 3: Container Insights (Métricas Avançadas)

> **Contexto:** Logs mostram "o que aconteceu". Métricas mostram "como está agora". Container Insights coleta métricas de performance de cada pod, node e cluster — CPU, memória, rede, disco. Isso permite identificar gargalos, prever problemas e dimensionar recursos corretamente.
>
> **Conceitos-chave:**
> - **Container Insights:** Solução da AWS que coleta métricas detalhadas de containers automaticamente
> - **CloudWatch Agent:** Daemon que coleta e envia métricas do node para o CloudWatch
> - **Métricas de Performance:** CPU utilization, Memory utilization, Network I/O, Disk I/O — por pod, por node, por cluster
> - **Namespace de métricas:** `ContainerInsights` — onde todas as métricas de containers ficam agrupadas

### 3.1 Habilitando Container Insights no Cluster

```bash
# Habilitar Container Insights via add-on
aws eks update-addon \
  --cluster-name $CLUSTER_NAME \
  --addon-name amazon-cloudwatch-observability \
  --region $AWS_REGION 2>/dev/null || \
aws eks create-addon \
  --cluster-name $CLUSTER_NAME \
  --addon-name amazon-cloudwatch-observability \
  --region $AWS_REGION

echo "✅ Container Insights habilitado"
```

> [!NOTE]
> Se o addon não estiver disponível, podemos instalar o CloudWatch Agent manualmente (passo 3.2 alternativo).

### 3.2 Alternativa: CloudWatch Agent via Manifesto

```bash
# Se o addon não funcionar, usar manifesto manual
kubectl apply -f https://raw.githubusercontent.com/aws-samples/amazon-cloudwatch-container-insights/latest/k8s-deployment-manifest-templates/deployment-mode/daemonSet/container-insights-monitoring/cwagent/cwagent-daemonset.yaml

# Verificar agent rodando
kubectl get pods -n amazon-cloudwatch -l name=cloudwatch-agent
```

### 3.3 Verificando Métricas no CloudWatch

```bash
# Listar métricas disponíveis do Container Insights
aws cloudwatch list-metrics \
  --namespace ContainerInsights \
  --dimensions Name=ClusterName,Value=$CLUSTER_NAME \
  --query 'Metrics[].MetricName' \
  --output text

# Consultar CPU do cluster nos últimos 10 minutos
```

## Seção 4: Criando Alertas (CloudWatch Alarms)

> **Contexto:** Métricas e logs são úteis para diagnóstico, mas não resolvem o problema de "ninguém estava olhando quando caiu". Alertas automatizados monitoram métricas 24/7 e notificam a equipe quando algo sai do normal — antes que os usuários percebam.
>
> **Conceitos-chave:**
> - **CloudWatch Alarm:** Monitora uma métrica e muda de estado (OK → ALARM) quando ultrapassa um threshold
> - **Threshold:** Valor limite que define "normal" vs "anômalo" (ex: CPU > 80% = problema)
> - **Evaluation Periods:** Quantos períodos consecutivos precisam ultrapassar o threshold antes de disparar (evita falsos positivos)
> - **SNS (Simple Notification Service):** Serviço de notificações — envia email, SMS ou aciona Lambda quando o alarme dispara

### 4.1 Criando Alarme de CPU Alta

```bash
# Alarme: CPU média > 70% por 2 períodos de 5 minutos
aws cloudwatch put-metric-alarm \
  --alarm-name "EKS-ADS-HighCPU" \
  --alarm-description "CPU acima de 70% no cluster ADS" \
  --namespace ContainerInsights \
  --metric-name pod_cpu_utilization \
  --dimensions Name=ClusterName,Value=$CLUSTER_NAME \
  --statistic Average \
  --period 300 \
  --threshold 70 \
  --comparison-operator GreaterThanThreshold \
  --evaluation-periods 2 \
  --treat-missing-data notBreaching

echo "✅ Alarme de CPU criado"
```

### 4.2 Criando Alarme de Memória Alta

```bash
# Alarme: Memória média > 80% por 2 períodos de 5 minutos
aws cloudwatch put-metric-alarm \
  --alarm-name "EKS-ADS-HighMemory" \
  --alarm-description "Memória acima de 80% no cluster ADS" \
  --namespace ContainerInsights \
  --metric-name pod_memory_utilization \
  --dimensions Name=ClusterName,Value=$CLUSTER_NAME \
  --statistic Average \
  --period 300 \
  --threshold 80 \
  --comparison-operator GreaterThanThreshold \
  --evaluation-periods 2 \
  --treat-missing-data notBreaching

echo "✅ Alarme de Memória criado"
```

### 4.3 Criando Alarme de Pods Não Saudáveis

```bash
# Alarme: Pods em estado não-Running
aws cloudwatch put-metric-alarm \
  --alarm-name "EKS-ADS-UnhealthyPods" \
  --alarm-description "Pods não saudáveis no namespace ads-unifaat" \
  --namespace ContainerInsights \
  --metric-name pod_status_failed \
  --dimensions Name=ClusterName,Value=$CLUSTER_NAME Name=Namespace,Value=$NAMESPACE \
  --statistic Sum \
  --period 60 \
  --threshold 1 \
  --comparison-operator GreaterThanOrEqualToThreshold \
  --evaluation-periods 1 \
  --treat-missing-data notBreaching

echo "✅ Alarme de Pods não saudáveis criado"
```

### 4.4 Verificando Alarmes Criados

```bash
# Listar todos os alarmes
aws cloudwatch describe-alarms \
  --alarm-name-prefix "EKS-ADS" \
  --query 'MetricAlarms[].{Nome:AlarmName,Estado:StateValue,Threshold:Threshold}' \
  --output table
```

> [!NOTE]
> **Resultado Esperado:** 3 alarmes listados, todos com estado `OK` (se a aplicação está saudável).

## Seção 5: CloudWatch Logs Insights (Análise de Logs)

> **Contexto:** Ter logs armazenados é ótimo, mas procurar informação em milhares de linhas de log é como procurar agulha no palheiro. CloudWatch Logs Insights permite fazer **queries estruturadas** nos logs — filtrar por padrão, agregar por tempo, contar erros. É o "SQL dos logs".
>
> **Conceitos-chave:**
> - **Logs Insights:** Engine de query da AWS para logs — syntax própria similar a SQL
> - **fields:** Seleciona quais campos mostrar
> - **filter:** Filtra eventos por padrão (equivalente ao WHERE do SQL)
> - **stats:** Agrega dados (count, avg, sum — equivalente ao GROUP BY)
> - **bin():** Agrupa por intervalo de tempo (ex: a cada 5 minutos)

### 5.1 Queries de Análise

```bash
# Query 1: Últimos 20 logs da aplicação
cat > query-recent.txt << 'EOF'
fields @timestamp, @message, @logStream
| sort @timestamp desc
| limit 20
EOF

echo "=== Query: Logs Recentes ==="
cat query-recent.txt
echo ""
echo "Execute no Console AWS: CloudWatch > Logs Insights > Selecione o Log Group: $LOG_GROUP"
```

### 5.2 Query para Encontrar Erros

```bash
# Query 2: Filtrar apenas erros
cat > query-errors.txt << 'EOF'
fields @timestamp, @message
| filter @message like /error|ERROR|Error|500|503/
| sort @timestamp desc
| limit 50
EOF

echo "=== Query: Erros ==="
cat query-errors.txt
```

### 5.3 Query para Contagem de Requisições

```bash
# Query 3: Contar requisições por intervalo de 5 minutos
cat > query-requests.txt << 'EOF'
fields @timestamp, @message
| filter @message like /GET|POST|PUT|DELETE/
| stats count() as total_requests by bin(5m)
| sort @timestamp desc
EOF

echo "=== Query: Requisições por Período ==="
cat query-requests.txt
```

### 5.4 Executando Query via CLI

```bash
# Iniciar query (retorna queryId)
QUERY_ID=$(aws logs start-query \
  --log-group-name $LOG_GROUP \
  --start-time $(date -d '1 hour ago' +%s) \
  --end-time $(date +%s) \
  --query-string 'fields @timestamp, @message | sort @timestamp desc | limit 10' \
  --query 'queryId' \
  --output text)

echo "Query ID: $QUERY_ID"

# Aguardar resultado (queries são assíncronas)
sleep 5

# Obter resultados
aws logs get-query-results --query-id $QUERY_ID
```



## Seção 6: Gerando Tráfego e Observando Métricas

> **Contexto:** Para ver o monitoramento em ação, precisamos gerar tráfego na aplicação. Vamos simular acessos e observar como as métricas reagem em tempo real. Isso demonstra o valor prático do monitoramento — ver a correlação entre carga e uso de recursos.
>
> **Conceitos-chave:**
> - **Load testing:** Simulação de carga para testar comportamento sob stress
> - **Baseline:** Métricas em estado normal (sem carga) — serve como referência
> - **Spike:** Aumento repentino de tráfego — revela gargalos

### 6.1 Obtendo o Endpoint

```bash
# Obter URL da aplicação (do Lab013)
ENDPOINT=$(kubectl get svc ads-site-service -n $NAMESPACE \
  -o jsonpath='{.status.loadBalancer.ingress[0].hostname}' 2>/dev/null)

if [ -z "$ENDPOINT" ]; then
  echo "⚠️ LoadBalancer não encontrado. Verifique se o service está rodando:"
  echo "kubectl get svc -n $NAMESPACE"
else
  echo "Endpoint: http://$ENDPOINT"
fi
```

### 6.2 Gerando Tráfego Simulado

```bash
# Gerar 100 requisições para a aplicação
echo "Gerando tráfego..."
for i in $(seq 1 100); do
  curl -s -o /dev/null -w "%{http_code}" http://$ENDPOINT
  echo " - Request $i"
done

echo "✅ 100 requisições enviadas"
```

### 6.3 Script de Carga Contínua

```bash
# Script para gerar carga por 2 minutos
cat > load-test.sh << 'EOF'
#!/bin/bash
ENDPOINT=$1
DURATION=120  # 2 minutos
END_TIME=$(($(date +%s) + DURATION))

echo "Gerando carga em $ENDPOINT por $DURATION segundos..."
COUNT=0

while [ $(date +%s) -lt $END_TIME ]; do
  curl -s -o /dev/null http://$ENDPOINT
  COUNT=$((COUNT + 1))
done

echo "✅ Total de requisições: $COUNT"
EOF

chmod +x load-test.sh

# Executar (em background para não travar o terminal)
./load-test.sh $ENDPOINT &
LOAD_PID=$!
echo "Load test rodando (PID: $LOAD_PID). Aguarde 2 minutos..."
```

### 6.4 Observando Métricas Durante a Carga

```bash
# Verificar uso de CPU dos pods em tempo real
kubectl top pods -n $NAMESPACE

# Verificar uso nos nodes
kubectl top nodes

# Verificar logs mais recentes (tráfego gerando access logs)
kubectl logs -n $NAMESPACE -l app=ads-site --tail=20
```

### 6.5 Parando o Teste de Carga

```bash
# Parar o load test
kill $LOAD_PID 2>/dev/null
echo "✅ Load test parado"
```

## Seção 8: Boas Práticas de Monitoramento

> **Contexto:** Saber configurar ferramentas é importante, mas saber **o que monitorar** e **como reagir** é o que diferencia um profissional experiente. Esta seção consolida as melhores práticas da indústria.

### 8.1 Os 4 Golden Signals (Google SRE)

| Signal | O que mede | Exemplo no nosso lab |
|--|--||
| **Latência** | Tempo de resposta | Tempo que o Nginx leva para responder |
| **Tráfego** | Volume de requisições | Requests por segundo no LoadBalancer |
| **Erros** | Taxa de falhas | Respostas HTTP 5xx |
| **Saturação** | Uso de recursos | CPU e Memória dos pods |

### 8.2 Regras de Ouro para Alertas

```
✅ BOM ALERTA:
- Específico: "CPU > 80% por 5 min no pod ads-site"
- Acionável: você sabe O QUE FAZER quando recebe
- Urgente: indica problema real que afeta usuários

❌ MAU ALERTA:
- Genérico: "algo está diferente"
- Frequente demais: gera fadiga de alertas
- Não-acionável: "disco em 50%" (e daí?)
```

## Seção 9: Limpeza do Ambiente

> **Contexto:** Como sempre, recursos AWS geram custo. CloudWatch Logs cobra por volume armazenado, Container Insights cobra por métricas coletadas. Limpamos tudo para não gerar custos inesperados.
>
> **Conceitos-chave:**
> - **Retenção de logs:** Logs mais antigos que o período configurado são deletados automaticamente
> - **Dashboard:** Dashboards personalizados custam $3/mês cada
> - **Alarmes:** Custam ~$0.10/mês cada (10 alarmes grátis no Free Tier)

### 9.1 Removendo Recursos de Monitoramento

```bash
# Deletar alarmes
aws cloudwatch delete-alarms \
  --alarm-names "EKS-ADS-HighCPU" "EKS-ADS-HighMemory" "EKS-ADS-UnhealthyPods"

echo "✅ Alarmes removidos"

# Deletar dashboard
aws cloudwatch delete-dashboards \
  --dashboard-names "EKS-ADS-Dashboard"

echo "✅ Dashboard removido"

# Deletar log groups
aws logs delete-log-group \
  --log-group-name $LOG_GROUP 2>/dev/null

aws logs delete-log-group \
  --log-group-name "/aws/eks/$CLUSTER_NAME/cluster" 2>/dev/null

echo "✅ Log Groups removidos"
```

### 9.2 Removendo Fluent Bit e CloudWatch Agent

```bash
echo "✅ Agentes de monitoramento removidos"
```

### 9.3 Removendo Política IAM Inline

```bash
# Remover política inline adicionada à role dos nodes

  --role-name EKSNodeRole-ADS \
  --policy-name CloudWatchLogsAccess

```

## Resumo dos Conceitos Aprendidos

| Conceito | O que é | Para que serve |
|-||-|
| **CloudWatch Logs** | Serviço de logs centralizado | Armazenar e pesquisar logs de containers |
| **Container Insights** | Métricas de containers | Monitorar CPU/Memória/Rede por pod e node |
| **CloudWatch Alarms** | Alertas automatizados | Notificar quando métricas saem do normal |
| **Logs Insights** | Engine de query de logs | Analisar padrões, contar erros, correlacionar |
| **Fluent Bit** | Coletor de logs | Envia logs dos pods para o CloudWatch |
| **DaemonSet** | Pod em cada node | Garante agente de coleta em todo o cluster |
| **Dashboard** | Painel visual | Visão consolidada do estado do sistema |
| **Golden Signals** | 4 métricas essenciais | Latência, Tráfego, Erros, Saturação |
