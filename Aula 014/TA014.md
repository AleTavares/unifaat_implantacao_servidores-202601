## 1. Conceitos Fundamentais

### A Importância da Observabilidade em Produção

Quando sua aplicação está rodando em produção com centenas de containers distribuídos, você precisa responder perguntas como:
- "Por que a aplicação está lenta?"
- "Qual container está consumindo mais CPU?"
- "Onde está o gargalo na jornada do usuário?"
- "Quantos erros 500 tivemos na última hora?"

Sem **observabilidade**, você está "voando cego". É como dirigir um carro sem painel - você não sabe a velocidade, combustível ou se há problemas no motor.

### Os Três Pilares da Observabilidade

#### 1. Logs (O que aconteceu?)
**Logs** são registros de eventos discretos com timestamp:
```json
{
  "timestamp": "2026-01-15T10:30:00Z",
  "level": "ERROR",
  "service": "user-api",
  "message": "Database connection timeout",
  "user_id": "12345",
  "request_id": "abc-123",
  "duration_ms": 5000
}
```

#### 2. Métricas (Quanto/Como está?)
**Métricas** são valores numéricos ao longo do tempo:
- CPU: 75%
- Memória: 2.1GB/4GB
- Requests/segundo: 150
- Latência média: 200ms
- Taxa de erro: 0.5%

#### 3. Traces (Qual o caminho?)
**Traces** rastreiam uma requisição através de múltiplos serviços:
```
User Request → Load Balancer → API Gateway → Auth Service → User Service → Database
     100ms         5ms           10ms         50ms         200ms        300ms
```

### Amazon CloudWatch: O Centro Nervoso

**CloudWatch** é o sistema de monitoramento nativo da AWS que coleta, armazena e visualiza dados de observabilidade.

#### CloudWatch Logs
**Log Groups** organizam logs relacionados:
```bash
# Estrutura típica
/aws/ecs/minha-aplicacao
├── /aws/ecs/minha-aplicacao/web-container/task-123
├── /aws/ecs/minha-aplicacao/web-container/task-456
└── /aws/ecs/minha-aplicacao/api-container/task-789
```

**Log Streams** são sequências de eventos de uma fonte específica:
```bash
# Visualizar logs
aws logs describe-log-groups
aws logs describe-log-streams --log-group-name /aws/ecs/minha-app
aws logs get-log-events --log-group-name /aws/ecs/minha-app --log-stream-name task-123
```

#### CloudWatch Metrics
**Métricas padrão** são coletadas automaticamente:
- EC2: CPUUtilization, NetworkIn/Out, DiskReadOps
- ECS: CPUUtilization, MemoryUtilization
- ALB: RequestCount, TargetResponseTime, HTTPCode_Target_2XX_Count

**Métricas customizadas** você envia da aplicação:
```bash
# Enviar métrica customizada
aws cloudwatch put-metric-data \
  --namespace "MyApp/Orders" \
  --metric-data MetricName=OrdersProcessed,Value=42,Unit=Count
```

#### CloudWatch Alarms
**Alarms** monitoram métricas e executam ações:
```bash
# Criar alarm para CPU alta
aws cloudwatch put-metric-alarm \
  --alarm-name "High-CPU" \
  --alarm-description "CPU usage above 80%" \
  --metric-name CPUUtilization \
  --namespace AWS/ECS \
  --statistic Average \
  --period 300 \
  --threshold 80 \
  --comparison-operator GreaterThanThreshold \
  --evaluation-periods 2
```

### Container Insights: Visibilidade Profunda

**Container Insights** oferece métricas detalhadas para containers:

#### Habilitando Container Insights
```bash
# Para ECS
aws ecs put-account-setting \
  --name containerInsights \
  --value enabled

# Para EKS
curl https://raw.githubusercontent.com/aws-samples/amazon-cloudwatch-container-insights/latest/k8s-deployment-manifest-templates/deployment-mode/daemonset/container-insights-monitoring/quickstart/cwagent-fluentd-quickstart.yaml | kubectl apply -f -
```

#### Métricas Disponíveis
- **Cluster Level**: CPU, Memory, Network, Storage por cluster
- **Service Level**: CPU, Memory, Network por service
- **Task Level**: CPU, Memory, Network por task individual
- **Container Level**: CPU, Memory por container

### Structured Logging: Logs Inteligentes

#### Log Não Estruturado (Ruim)
```
2026-01-15 10:30:00 ERROR: User 12345 failed to login from IP 192.168.1.100
```

#### Log Estruturado (Bom)
```json
{
  "timestamp": "2026-01-15T10:30:00Z",
  "level": "ERROR",
  "event": "login_failed",
  "user_id": "12345",
  "source_ip": "192.168.1.100",
  "reason": "invalid_password",
  "attempt_count": 3
}
```

#### Vantagens do Structured Logging
- **Searchable**: Fácil de pesquisar e filtrar
- **Aggregatable**: Pode ser agregado e analisado
- **Alertable**: Pode gerar alertas automáticos
- **Dashboardable**: Pode ser visualizado em dashboards

### CloudWatch Logs Insights: SQL para Logs

**Logs Insights** permite queries SQL-like nos logs:

```sql
-- Top 10 IPs com mais requests
fields @timestamp, source_ip
| filter @message like /ERROR/
| stats count() by source_ip
| sort count desc
| limit 10

-- Latência média por endpoint
fields @timestamp, endpoint, duration
| filter @type = "REQUEST"
| stats avg(duration) by endpoint
| sort avg desc

-- Erros por hora
fields @timestamp
| filter level = "ERROR"
| stats count() by bin(5m)
```

### Alerting Inteligente

#### Threshold-based Alerts
```bash
# Alerta simples: CPU > 80%
aws cloudwatch put-metric-alarm \
  --alarm-name "HighCPU" \
  --threshold 80 \
  --comparison-operator GreaterThanThreshold
```

#### Anomaly Detection
```bash
# Detecção de anomalias com ML
aws cloudwatch put-anomaly-detector \
  --namespace AWS/ECS \
  --metric-name CPUUtilization \
  --stat Average
```

#### Composite Alarms
```bash
# Alarm composto: CPU alta E memória alta
aws cloudwatch put-composite-alarm \
  --alarm-name "HighResourceUsage" \
  --alarm-rule "(ALARM HighCPU) AND (ALARM HighMemory)"
```

### Cost Optimization para Monitoramento

#### Log Retention Policies
```bash
# Configurar retenção de logs
aws logs put-retention-policy \
  --log-group-name /aws/ecs/minha-app \
  --retention-in-days 30
```

#### Metric Filters
```bash
# Filtrar apenas logs de erro para métricas
aws logs put-metric-filter \
  --log-group-name /aws/ecs/minha-app \
  --filter-name ErrorCount \
  --filter-pattern "ERROR" \
  --metric-transformations \
    metricName=ErrorCount,metricNamespace=MyApp,metricValue=1
```

## 2. Questões de Múltipla Escolha

### Questão 1
Uma aplicação de e-commerce está apresentando lentidão esporádica. Para investigar se o problema é CPU alta, latência de banco de dados ou gargalo de rede, qual combinação dos pilares da observabilidade seria mais eficaz?

a) Apenas logs de erro da aplicação
b) Métricas de CPU + Traces de requisições + Logs de transações
c) Apenas métricas de CPU e memória
d) Apenas traces distribuídos

**Gabarito: B**

**Justificativa:** Para investigar lentidão esporádica, você precisa dos três pilares trabalhando juntos: **Métricas** mostram se há sobrecarga de recursos (CPU, memória), **Traces** revelam onde na jornada da requisição está o gargalo (frontend, API, banco), e **Logs** fornecem detalhes específicos sobre erros ou operações lentas. Cada pilar sozinho não fornece o contexto completo.

### Questão 2
Você configurou um container ECS para enviar logs para CloudWatch, mas os logs não estão aparecendo. Qual é a causa mais provável?

a) O container não tem acesso à internet
b) A task não tem permissão IAM para escrever no CloudWatch
c) O log group não existe
d) Todas as alternativas são possíveis

**Gabarito: D**

**Justificativa:** Logs não aparecerem pode ter múltiplas causas: **Permissão IAM** (taskRoleArn precisa de CloudWatchLogsFullAccess), **Log group inexistente** (deve ser criado antes ou configurado para criação automática), ou **Conectividade** (Security Groups bloqueando HTTPS para CloudWatch). Um troubleshooting sistemático deve verificar todas essas possibilidades.

### Questão 3
Sua aplicação tem picos de tráfego previsíveis (Black Friday, horário comercial). Qual estratégia de alertas evitaria falsos positivos durante esses picos?

a) Aumentar o threshold de CPU permanentemente
b) Usar CloudWatch Anomaly Detection
c) Desabilitar alertas durante eventos conhecidos
d) Configurar alertas apenas para erros 5xx

**Gabarito: B**

**Justificativa:** **CloudWatch Anomaly Detection** usa machine learning para aprender padrões históricos, incluindo sazonalidade. Ele entende que "CPU 85% na Black Friday às 14h" é normal, mas "CPU 85% numa terça-feira às 3h" é anômalo. Aumentar threshold permanentemente pode mascarar problemas reais, desabilitar alertas é perigoso, e alertas apenas para 5xx podem perder degradação de performance.
