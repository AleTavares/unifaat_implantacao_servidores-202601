# Lab 13: Deploy de Containers na AWS com EKS (Elastic Kubernetes Service)

**Disciplina:** Implementação de servidor e nuvem (cloud)  
**Aula:** 13 - Deploy de Containers na AWS com EKS  
**Objetivo:** Implementar o deploy completo de uma aplicação containerizada no AWS EKS, desde a construção da imagem até o acesso público via LoadBalancer.

## Objetivo do Lab

Ao final deste laboratório, você será capaz de:
- Construir e publicar imagens Docker no AWS ECR
- Criar e configurar um cluster EKS completo
- Realizar deploy de aplicações usando manifestos Kubernetes
- Expor aplicações ao mundo via LoadBalancer
- Monitorar e debugar pods no cluster
- Realizar limpeza completa de recursos AWS

### Pré-requisitos

* AWS CLI configurada (Aula 11)
* Docker Desktop rodando no WSL
* kubectl instalado
* Imagem base no ECR ou Dockerfile pronto
* Credenciais AWS com permissões EKS/ECR/IAM/CloudFormation

## Cenário: A Vitrine Digital do Curso de ADS

### O Desafio

Imagine a seguinte situação: a coordenação do curso de **Análise e Desenvolvimento de Sistemas** da UniFAAT precisa de uma página web institucional para apresentar o curso em eventos, feiras educacionais e campanhas de vestibular. Essa página precisa estar **sempre disponível**, **escalar automaticamente** em picos de acesso (como durante o período de inscrições) e ser **fácil de atualizar** pelos desenvolvedores.

### O Problema com Abordagens Tradicionais

No passado, colocar um site no ar significava:
- Comprar ou alugar um servidor físico
- Instalar e configurar o sistema operacional manualmente
- Instalar o servidor web (Apache, Nginx) na mão
- Rezar para o servidor não cair no dia do vestibular
- Escalar? Só comprando outro servidor...

### A Solução Moderna: Containers + Kubernetes na Nuvem

Como futuros profissionais de TI, vocês vão resolver esse problema da forma que o mercado faz hoje:

1. **Containerizar** a aplicação com Docker (empacotamento padronizado)
2. **Armazenar** a imagem no ECR (registro seguro na nuvem)
3. **Orquestrar** com Kubernetes no EKS (escalabilidade automática)
4. **Expor** ao mundo com LoadBalancer (alta disponibilidade)

### Por que EKS?

| Benefício | Descrição |
|--|--|
| **Escalabilidade** | Kubernetes escala pods automaticamente conforme demanda |
| **Resiliência** | Se um pod morre, outro é criado automaticamente |
| **Portabilidade** | Mesmo YAML funciona em qualquer cluster K8s |
| **Padrão de Mercado** | Kubernetes é o padrão global de orquestração |
| **Integração AWS** | EKS se integra nativamente com ECR, IAM, CloudWatch |

> 💡 **Analogia:** Pense no EKS como um "gerente de restaurante" que garante que sempre haverá garçons (pods) suficientes atendendo os clientes (requisições), mesmo que um garçom tire folga (falha). O gerente automaticamente chama substitutos!

## Seção 3: Publicando a Imagem no ECR

> **Contexto:** Com a imagem Docker funcionando localmente, precisamos disponibilizá-la na nuvem para que o cluster EKS possa acessá-la. É como enviar seu código para o GitHub — mas para imagens Docker. O ECR (Elastic Container Registry) é o "GitHub de imagens Docker" da AWS: privado, seguro e integrado nativamente com EKS.
>
> **Conceitos-chave:**
> - **ECR (Elastic Container Registry):** Registro privado de imagens Docker na AWS. Armazena, versiona e distribui imagens com segurança
> - **Registry vs Repository:** Registry é o serviço (ECR). Repository é onde ficam as versões de uma imagem específica (como um "repo" no GitHub)
> - **Docker Tag:** Marcação que associa uma imagem local a um endereço remoto (URI do ECR). Não altera a imagem — apenas cria uma referência
> - **Docker Push:** Envia as camadas (layers) da imagem para o registry remoto
> - **Autenticação temporária:** O token ECR expira em 12 horas por segurança — padrão de credenciais efêmeras

### 3.1 Criando o Repositório ECR

```bash
# Voltar ao diretório principal do lab
cd ~/aulas_lab/aula013

# Criar repositório ECR
aws ecr create-repository \
  --repository-name $REPO_NAME \
  --region $AWS_REGION
```

### 3.2 Autenticando Docker com ECR

```bash
# Login no ECR
aws ecr get-login-password --region $AWS_REGION | \
  docker login --username AWS --password-stdin $AWS_ACCOUNT_ID.dkr.ecr.$AWS_REGION.amazonaws.com
```

> [!NOTE]

## Seção 4: Configurando o Cluster EKS

> **Contexto:** Esta é a seção mais densa do lab — aqui criamos toda a infraestrutura necessária para rodar Kubernetes na AWS. Um cluster EKS é composto por um **Control Plane** (gerenciado pela AWS) e **Worker Nodes** (instâncias EC2 que executam seus containers). Antes de criar o cluster, precisamos configurar permissões (IAM Roles) e rede (VPC), pois na AWS tudo segue o princípio de menor privilégio.
>
> **Conceitos-chave:**
> - **EKS (Elastic Kubernetes Service):** Kubernetes gerenciado pela AWS. A AWS cuida do Control Plane (API server, etcd, scheduler) — você gerencia apenas os nodes
> - **IAM Role:** Identidade com permissões que pode ser assumida por um serviço AWS. Diferente de um user, uma role não tem senha — é usada por máquinas/serviços
> - **Assume Role Policy:** Define QUEM pode assumir a role (no caso, o serviço EKS ou EC2)
> - **VPC (Virtual Private Cloud):** Rede virtual isolada na AWS. O cluster precisa de uma VPC com subnets públicas e privadas
> - **CloudFormation:** Serviço de IaC (Infrastructure as Code) da AWS — cria infraestrutura a partir de templates YAML/JSON
> - **Node Group:** Conjunto de instâncias EC2 que se registram automaticamente no cluster como "workers"
> - **kubeconfig:** Arquivo de configuração que diz ao kubectl como se conectar ao cluster (endpoint, certificados, autenticação)

### 4.1 Criando Role IAM para o Cluster

> **Por quê?** O EKS precisa de permissões para gerenciar recursos AWS em seu nome (criar load balancers, gerenciar ENIs de rede, etc). A role `EKSClusterRole-ADS` dá essas permissões ao serviço EKS.

```bash
# Criar role para o cluster EKS
aws iam create-role \
  --role-name EKSClusterRole-ADS \
  --assume-role-policy-document '{
    "Version": "2012-10-17",
    "Statement": [
      {
        "Effect": "Allow",
        "Principal": {
          "Service": "eks.amazonaws.com"
        },
        "Action": "sts:AssumeRole"
      }
    ]
  }'

# Anexar política necessária
aws iam attach-role-policy \
  --policy-arn arn:aws:iam::aws:policy/AmazonEKSClusterPolicy \
  --role-name EKSClusterRole-ADS
```

### 4.2 Criando Role IAM para os Worker Nodes

> **Por quê?** Os nodes (máquinas EC2) precisam de permissões para: se comunicar com o cluster (WorkerNodePolicy), gerenciar rede entre pods (CNI_Policy) e puxar imagens do ECR (ContainerRegistryReadOnly).

```bash
# Criar role para os nodes
aws iam create-role \
  --role-name EKSNodeRole-ADS \
  --assume-role-policy-document '{
    "Version": "2012-10-17",
    "Statement": [{
      "Effect": "Allow",
      "Principal": {"Service": "ec2.amazonaws.com"},
      "Action": "sts:AssumeRole"
    }]
  }'

# Anexar políticas necessárias (3 políticas)
aws iam attach-role-policy \
  --role-name EKSNodeRole-ADS \
  --policy-arn arn:aws:iam::aws:policy/AmazonEKSWorkerNodePolicy

aws iam attach-role-policy \
  --role-name EKSNodeRole-ADS \
  --policy-arn arn:aws:iam::aws:policy/AmazonEKS_CNI_Policy

aws iam attach-role-policy \
  --role-name EKSNodeRole-ADS \
  --policy-arn arn:aws:iam::aws:policy/AmazonEC2ContainerRegistryReadOnly
```

> [!IMPORTANT]
> A política `AmazonEC2ContainerRegistryReadOnly` é essencial para que os nodes consigam puxar imagens do ECR.

### 4.3 Criando a VPC com CloudFormation

> **Por quê?** Um cluster EKS precisa de uma rede isolada com subnets em múltiplas Availability Zones (para alta disponibilidade). O template oficial da AWS cria automaticamente uma VPC com subnets públicas e privadas, route tables, internet gateway e NAT gateway — tudo que o cluster precisa para funcionar.

```bash
# Criar VPC usando template oficial da AWS para EKS
aws cloudformation create-stack \
  --stack-name eks-vpc-ads \
  --template-url https://s3.us-west-2.amazonaws.com/amazon-eks/cloudformation/2020-10-29/amazon-eks-vpc-private-subnets.yaml

# Aguardar criação (pode levar 2-3 minutos)
echo "Aguardando criação da VPC..."
aws cloudformation wait stack-create-complete --stack-name eks-vpc-ads
echo "VPC criada com sucesso!"
```

### 4.4 Obtendo IDs das Subnets

> **Por quê?** O cluster e os nodes precisam saber em quais subnets da VPC serão provisionados. O CloudFormation expõe esses IDs como "Outputs" do stack.

```bash
# Obter subnet IDs criadas pelo CloudFormation
SUBNET_IDS=$(aws cloudformation describe-stacks \
  --stack-name eks-vpc-ads \
  --query 'Stacks[0].Outputs[?OutputKey==`SubnetIds`].OutputValue' \
  --output text)

echo "Subnets: $SUBNET_IDS"
```

### 4.5 Criando o Cluster EKS

> **Por quê?** Este é o coração da infraestrutura — o Control Plane do Kubernetes. Ele gerencia o estado desejado do cluster, agenda pods nos nodes e expõe a API do Kubernetes. A AWS gerencia totalmente este componente (patches, backups, alta disponibilidade).

```bash
# Criar cluster EKS
aws eks create-cluster \
  --name $CLUSTER_NAME \
  --role-arn $(aws iam get-role --role-name EKSClusterRole-ADS --query 'Role.Arn' --output text) \
  --resources-vpc-config subnetIds=$SUBNET_IDS \
  --kubernetes-version 1.32

echo "Cluster sendo criado... Isso leva ~10-15 minutos."
echo "Você pode verificar o progresso com: aws eks describe-cluster --name $CLUSTER_NAME --query 'cluster.status'"
```

### 4.6 Aguardando o Cluster Ficar Ativo

```bash
# Aguardar cluster ficar ativo (paciência! ~10-15 min)
aws eks wait cluster-active --name $CLUSTER_NAME
echo "✅ Cluster $CLUSTER_NAME está ATIVO!"
```

> [!WARNING]
> ⏱️ **Este passo demora!** O cluster EKS leva entre 10-15 minutos para ficar pronto. Aproveite para revisar os conceitos de Kubernetes enquanto aguarda.

### 4.7 Criando o Node Group

> **Por quê?** O Control Plane sozinho não executa containers — ele apenas "orquestra". Os Node Groups são as máquinas reais (EC2 t3.medium) que rodam os pods. O `scaling-config` define elasticidade: mínimo 2 nodes (resiliência), máximo 3 (controle de custo), desejado 2 (padrão).

```bash
# Criar node group (máquinas que rodarão os pods)
aws eks create-nodegroup \
  --cluster-name $CLUSTER_NAME \
  --nodegroup-name ads-app-nodes \
  --node-role $(aws iam get-role --role-name EKSNodeRole-ADS --query 'Role.Arn' --output text) \
  --subnets $(echo $SUBNET_IDS | tr ',' ' ') \
  --instance-types t3.medium \
  --scaling-config minSize=2,maxSize=3,desiredSize=2

echo "Node Group sendo criado... (~5 minutos)"
```

### 4.8 Aguardando Node Group Ficar Ativo

```bash
# Aguardar nodes ficarem prontos
aws eks wait nodegroup-active \
  --cluster-name $CLUSTER_NAME \
  --nodegroup-name ads-app-nodes

echo "✅ Node Group está ATIVO!"
```

### 4.9 Configurando kubectl

> **Por quê?** O `kubectl` precisa saber o endpoint do cluster, credenciais e certificado TLS para se comunicar. O comando `update-kubeconfig` configura tudo automaticamente no arquivo `~/.kube/config`.

```bash
# Configurar kubeconfig para acessar o cluster
aws eks update-kubeconfig --name $CLUSTER_NAME --region $AWS_REGION

# Verificar conexão
kubectl cluster-info

# Listar nodes
kubectl get nodes
```

> [!NOTE]
> **Resultado Esperado:** Você deve ver 2 nodes com status `Ready`.



## Seção 5: Deploy da Aplicação no EKS

> **Contexto:** Com o cluster pronto e o kubectl configurado, agora vamos "dizer ao Kubernetes o que queremos". No K8s, tudo é declarativo — você descreve o estado desejado em arquivos YAML (manifestos) e o Kubernetes se encarrega de torná-lo realidade. Se um pod cai, o K8s recria. Se você pede 3 réplicas, ele garante que existam 3.
>
> **Conceitos-chave:**
> - **Manifesto YAML:** Arquivo declarativo que descreve um recurso Kubernetes (Deployment, Service, Pod, etc)
> - **Namespace:** Isolamento lógico dentro do cluster. Permite organizar recursos e aplicar políticas separadas
> - **Deployment:** Controlador que garante que o número desejado de pods esteja sempre rodando. Gerencia rolling updates e rollbacks
> - **Service:** Abstração de rede que expõe pods. O tipo `LoadBalancer` cria automaticamente um ELB na AWS
> - **Labels e Selectors:** Sistema de "etiquetas" que conecta Services a Pods. O Service encontra seus pods pelo label `app: ads-site`
> - **Probes (liveness/readiness):** Health checks que o K8s usa para saber se o pod está saudável e pode receber tráfego

### 5.1 Criando o Namespace

```bash
# Criar namespace isolado para a aplicação
kubectl create namespace ads-unifaat
```

### 5.2 Criando o Deployment Manifest

```bash
# Criar arquivo deployment.yaml
cat << EOF > deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: ads-site
  namespace: ads-unifaat
  labels:
    app: ads-site
spec:
  replicas: 2
  selector:
    matchLabels:
      app: ads-site
  template:
    metadata:
      labels:
        app: ads-site
    spec:
      containers:
      - name: ads-site
        image: ${REPO_URI}:${IMAGE_TAG}
        ports:
        - containerPort: 80
        resources:
          requests:
            memory: "64Mi"
            cpu: "50m"
          limits:
            memory: "128Mi"
            cpu: "100m"
        livenessProbe:
          httpGet:
            path: /
            port: 80
          initialDelaySeconds: 10
          periodSeconds: 30
        readinessProbe:
          httpGet:
            path: /
            port: 80
          initialDelaySeconds: 5
          periodSeconds: 10
EOF
```

> 💡 **Entendendo o Deployment:**
> - `replicas: 2` → Duas cópias da aplicação rodando simultaneamente
> - `resources` → Limites de CPU e memória para cada pod
> - `livenessProbe` → Kubernetes verifica se o pod está "vivo"
> - `readinessProbe` → Kubernetes verifica se o pod pode receber tráfego

### 5.3 Criando o Service Manifest (LoadBalancer)

```bash
# Criar arquivo service.yaml
cat << EOF > service.yaml
apiVersion: v1
kind: Service
metadata:
  name: ads-site-service
  namespace: ads-unifaat
  labels:
    app: ads-site
spec:
  type: LoadBalancer
  ports:
  - port: 80
    targetPort: 80
    protocol: TCP
  selector:
    app: ads-site
EOF
```

> 💡 **Entendendo o Service:**
> - `type: LoadBalancer` → AWS cria automaticamente um ELB (Elastic Load Balancer)
> - `port: 80` → Porta exposta ao mundo
> - `targetPort: 80` → Porta do container Nginx
> - `selector` → Conecta o service aos pods com label `app: ads-site`

### 5.4 Aplicando os Manifestos

```bash
# Aplicar deployment
kubectl apply -f deployment.yaml

# Aplicar service
kubectl apply -f service.yaml

echo "✅ Manifestos aplicados!"
```

### 5.5 Verificando o Deploy

```bash
# Ver status do deployment
kubectl get deployments -n ads-unifaat

# Ver pods rodando
kubectl get pods -n ads-unifaat

# Ver service e LoadBalancer
kubectl get svc -n ads-unifaat
```

> [!NOTE]
> **Resultado Esperado:**
> - Deployment: 2/2 replicas disponíveis
> - Pods: 2 pods com status `Running`
> - Service: Status `EXTERNAL-IP` aparecerá como um DNS da AWS



## Seção 6: Acessando a Aplicação

> **Contexto:** O Service do tipo LoadBalancer dispara a criação automática de um Elastic Load Balancer (ELB) na AWS. Este ELB recebe um DNS público (hostname) que qualquer pessoa no mundo pode acessar. O tráfego é distribuído entre os pods saudáveis. É assim que aplicações reais ficam acessíveis na internet — sem expor IPs de máquinas diretamente.
>
> **Conceitos-chave:**
> - **ELB (Elastic Load Balancer):** Balanceador de carga gerenciado da AWS. Distribui tráfego, faz health check e escala automaticamente
> - **DNS propagation:** O hostname do ELB precisa de 1-3 minutos para se propagar nos servidores DNS
> - **Ingress vs LoadBalancer:** LoadBalancer cria um ELB por service. Para múltiplos services, usa-se Ingress Controller (conceito avançado)

## Seção 7: Monitoramento e Debug

> **Contexto:** Em produção, "deployou e funcionou" não é suficiente. Precisamos observar a aplicação continuamente: logs, métricas, eventos. O Kubernetes oferece ferramentas nativas para isso. Além disso, demonstramos aqui dois pilares fundamentais do K8s: **escalabilidade** (aumentar/diminuir replicas sob demanda) e **resiliência** (self-healing — o cluster se recupera sozinho de falhas).
>
> **Conceitos-chave:**
> - **kubectl logs:** Equivalente ao `docker logs`, mas para pods no cluster
> - **kubectl describe:** Mostra detalhes completos de um recurso, incluindo eventos e condições
> - **Scaling horizontal:** Adicionar mais réplicas (pods) para distribuir carga. Diferente de scaling vertical (dar mais CPU/RAM para uma máquina)
> - **Self-healing:** Se um pod é deletado/falha, o Deployment detecta que o estado atual ≠ estado desejado e cria um novo pod automaticamente
> - **Events:** Log de auditoria do K8s — mostra tudo que aconteceu (scheduling, pulling image, starting container, etc)

```bash
# Detalhes de um pod
kubectl describe pod -n ads-unifaat -l app=ads-site
```

### 7.3 Verificando Eventos

## Seção 8: Troubleshooting Comum

> **Contexto:** Problemas vão acontecer — e saber diagnosticá-los é uma das habilidades mais valorizadas no mercado. Esta seção documenta os erros mais comuns em deploys EKS e como investigá-los. O padrão é sempre: verificar eventos → verificar logs → verificar permissões → verificar rede.
>
> **Conceitos-chave:**
> - **ImagePullBackOff:** O node não conseguiu baixar a imagem do registry. Causas: imagem não existe, credenciais insuficientes, nome errado
> - **CrashLoopBackOff:** O container inicia e morre repetidamente. Causas: erro na aplicação, porta já em uso, variável de ambiente faltando
> - **Pending:** O pod não foi agendado em nenhum node. Causas: recursos insuficientes, node group não criado
> - **Princípio da investigação:** Sempre do mais específico (logs do pod) para o mais geral (eventos do namespace)

### Problema: Pods em status ImagePullBackOff

```bash
# Verificar se a imagem existe no ECR
aws ecr describe-images --repository-name $REPO_NAME --region $AWS_REGION

# Verificar se os nodes têm permissão para acessar o ECR
kubectl describe pod -n ads-unifaat -l app=ads-site | grep -A5 "Events"
```

**Solução:** Verifique se a política `AmazonEC2ContainerRegistryReadOnly` está anexada à role dos nodes.

### Problema: Service sem EXTERNAL-IP

```bash
# Verificar se o service foi criado corretamente
kubectl describe svc ads-site-service -n ads-unifaat

# Verificar eventos
kubectl get events -n ads-unifaat | grep -i loadbalancer
```

**Solução:** Aguarde 2-3 minutos. Se persistir, verifique se as subnets são públicas.

### Problema: Pods em CrashLoopBackOff

```bash
# Ver logs do pod com problema
kubectl logs -n ads-unifaat -l app=ads-site --previous
```

**Solução:** Geralmente indica erro na aplicação ou Dockerfile. Teste localmente primeiro.



## Seção 9: Limpeza Completa do Ambiente

> **Contexto:** Na AWS, você paga por recursos provisionados — mesmo que não estejam sendo usados. Um cluster EKS custa ~$0.10/hora (~$72/mês) só pelo Control Plane, mais o custo dos nodes EC2 (~$0.04/hora cada t3.medium). A limpeza segue uma **ordem específica**: primeiro remove-se o que está "dentro" (pods, services) para que o LoadBalancer AWS seja deletado, depois os nodes, depois o cluster, depois a VPC. Inverter essa ordem pode deixar recursos "órfãos" gerando custo.
>
> **Conceitos-chave:**
> - **Ordem de deleção:** Kubernetes resources → Node Group → Cluster → VPC → IAM Roles → ECR. Sempre de dentro para fora
> - **Recursos órfãos:** Se você deletar o cluster sem deletar o Service LoadBalancer antes, o ELB da AWS continuará existindo (e cobrando)
> - **FinOps:** Disciplina de gerenciamento financeiro em cloud. Regra #1: sempre limpar recursos de teste/lab
> - **`--force` no ECR:** Remove o repositório mesmo que contenha imagens. Em produção, nunca use sem confirmar

> [!IMPORTANT]
> ⚠️ **ATENÇÃO:** EKS cobra ~$0.10/hora pelo cluster e os nodes (t3.medium) também geram custos. **Sempre limpe após o lab!**

### 9.1 Removendo Recursos Kubernetes

```bash

kubectl delete -f service.yaml

# Deletar deployment
kubectl delete -f deployment.yaml

echo "✅ Recursos Kubernetes removidos"
```

| **ECR** | Registro de imagens | Armazena imagens Docker na AWS |
